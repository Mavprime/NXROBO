Spark Simulation - Commands

Workspace: ~/Documents/Extra/ROS Comp/simulation. There are two simulators and one real-robot check:

  • Kinematic sim on this PC, browser view at http://127.0.0.1:8090/; no ROS.
  • Gazebo sim on the Spark NUC (Ubuntu 20.04 / ROS Noetic), isolated on ROS master 11312.
  • Detection-bridge check on the real robot, passive, hardware master 11311.

Master rule: the hardware stack runs on 11311. Every simulation command in this sheet uses 11312 or no ROS at all. Never point the sim scripts at 11311.

No credentials or fixed IPs in this sheet. Passwords are not stored in the repository; use the operator's private notes. The robot IP is DHCP: read it from the launcher / robot_ip.txt (gitignored) or pass ROBOT_IP. Placeholders <robot-ip> and <pc-ip> in commands are intentional.

1. Kinematic simulation on the PC

No ROS, no robot. Runs fake_world.py + mission_logic.py and serves a canvas view from live_view.py.

cd "$HOME/Documents/Extra/ROS Comp/simulation/codes"

# full competition: board -> cake A -> bears B -> clocks C -> bananas D
python3 run_live.py --mission ../config/mission_competition.yaml --speed 2

# demo: A -> centre -> pick cake -> A
python3 run_live.py

Open http://127.0.0.1:8090/ after the viewer starts. The page shows the robot, lidar, trail, cubes, score, current fetch class and the step list.

The robot plans with A* around every field cube and the table, inflated by the robot radius plus 3 cm; FakeWorld.step also checks cube collision. It drives around the central cluster, not through it.

Options

--speed 2            # playback multiplier (sim time is unchanged)
--port 8090          # change if the port is busy
--start-delay 30     # wait before the mission starts
--linger 300         # keep serving after DONE (0 = until Ctrl+C)
--seed 7             # detection noise/dropout seed
--mission PATH       # mission YAML
--no-viewer          # console only
--no-realtime        # run as fast as possible (tests)
--report PATH        # write the run report JSON with per-step timings

Verified results

mission_competition.yaml: DONE, score 21, 340.1 s simulated, 0 collisions. Cake to A first, 3 bears to B, 3 clocks to C, 3 bananas to D; every placement verified. Demo mission: score 3, 28.6 s.

Missions and data

config/mission_demo.yaml           # cake demo
config/mission_competition.yaml    # cake + all 9 blocks, adaptive fetch
config/arena_map.yaml              # canonical 0..3 m arena (A top-left)
config/robot.yaml                  # measured chassis/arm parameters
config/gate.yaml                   # gate thresholds + injection
config/transform_3d.dat            # production 4x3 DLT pixel -> arm

The fetch step picks the nearest pending cube, drives to the closest Sorting side, gates/picks, then delivers to memory.mapping[class] and verifies.

2. Gazebo simulation on the Spark NUC

Spark is Ubuntu 20.04 / ROS Noetic with Gazebo Classic 11. The sim uses an isolated ROS master 11312 and a static arena map; the hardware stack on 11311 is never touched.

# Terminal 2 - synthetic truth detections + arm mock + mission node

# Markers for RViz

# RViz on the robot desktop :0 (viewed over VNC)

View: VNC to <robot-ip>:5900 (credentials as configured on the robot; not stored here). The sim_view.rviz layout includes Map, LaserScan, TF, RobotModel, /mission_markers and /detection_markers.

# Stop Gazebo, nav, mission, markers and RViz; 11311 stays up
bash ~/codes/robot/stop_sim.sh

Verified results

  • Nav goal Sorting_N (1.5, 1.88, -pi/2): status 3, Goal reached.
  • Full mission: DONE, cake delivered, all steps ok; goto 15.4 / 9.8 s, pick 3.4 s, place 2.0 s, verify 0.5 s (~31.7 s).
  • Gazebo model starts at (0.231, 2.780) yaw -0.793 — inside A. AMCL's localized pose is ~12 cm off but still inside the 0.45 m A square.

The Gazebo mission uses synthetic detections and an arm mock; it validates mission/nav/gate/verify, not physical perception or the real arm. Restart the sim for a fresh mission: the truth node has already moved the cubes.

3. RViz on the PC (ROS1 in Docker)

This PC has ROS 2 Humble; rviz2 cannot talk to a ROS 1 master. Use the Noetic container with the spark_sim:noetic image.

# One-time
sudo docker pull osrf/ros:noetic-desktop-full
cd "$HOME/Documents/Extra/ROS Comp/simulation/docker"
sudo docker build -t spark_sim:noetic .

# Robot Gazebo sim must be running on 11312
newgrp docker
ROBOT_IP= ./run_pc_rviz.sh

# Stop the PC viewer
sg docker -c 'docker stop pc_rviz'

run_pc_rviz.sh sets:

ROS_MASTER_URI=http://:11312   # current DHCP address
ROS_IP=                          # this PC LAN address
ROS_PACKAGE_PATH=/ws/assets             # Spark meshes
rviz -d /ws/ros/sim_view.rviz

The robot IP is DHCP. Read it from the launcher / robot_ip.txt (gitignored), or set ROBOT_IP; the PC IP is auto-detected unless PC_IP is set. The robot sim scripts bind the robot's LAN IP so remote RViz can connect.

Plain rosrun rviz rviz over SSH fails with could not connect to display. On the robot use DISPLAY=:0 XAUTHORITY=$HOME/.Xauthority, or the start_rviz_robot_sim.sh script, then view over VNC.

4b. Real camera web stream (MJPEG on :8080)

camera_stream.py serves the live D435 feed over HTTP so it opens in any browser. It subscribes to /camera/color/image_raw, so the camera driver must be running first. It uses the hardware master (11311); do not change ROS_MASTER_URI.

On the current Ubuntu Spark the script is at ~/auto/codes/camera_stream.py (older sheets say ~/codes/). Verify with ls ~/auto/codes/camera_stream.py before starting.

Check the driver

ssh spark@<robot-ip>
source /opt/ros/noetic/setup.bash
source ~/spark_noetic/devel/setup.bash

pgrep -af "roslaunch camera_driver_transfer"   # one launch, or nothing
timeout 5 rostopic hz /camera/color/image_raw  # expect ~30 Hz

No publisher and no rate means the driver is not streaming; the web page then answers 503 no frame yet. A bringup started with start_camera:=false does not start the camera — use the command below.

Start the driver (once)

source /opt/ros/noetic/setup.bash
source ~/spark_noetic/devel/setup.bash
setsid nohup roslaunch camera_driver_transfer d435.launch \
  > ~/logs/camera_driver.log 2>&1 < /dev/null &

Only one driver at a time. Starting a second camera_driver_transfer while one is running makes the RealSense nodelet exit with Bond broken, exiting, and the stream stays blank.

Start the streamer

source /opt/ros/noetic/setup.bash
setsid nohup python3 -u ~/auto/codes/camera_stream.py \
  > ~/logs/stream.log 2>&1 < /dev/null &

Open http://<robot-ip>:8080/; a single frame is at http://<robot-ip>:8080/snapshot.jpg.

Stop

fuser -k 8080/tcp          # stream server (only the listener on 8080)
pkill -f "[d]435.launch"   # camera driver (the [d] stops pkill matching its own shell)

Do not run pkill -f camera_stream.py in a command that also contains that path (for example the same SSH command that starts it): pkill -f matches its own shell and kills the session before the server starts. fuser -k 8080/tcp is sufficient.

4c. Production arm calibration (real robot)

Full command sheet: auto/docs/commands.html. There are two calibrations and they write different files:

  • Orange-pad DLT → ~/transform_3d.dat and ~/transform_3d.meta.json; used by grasp_generic.py and the current grasp tests.
  • Vendor red-square one-key → ~/thefile.txt; old vendor 2D path.
# active DLT check (SSH; base/camera/arm running)
python3 -u ~/codes/calib3d.py --check
# require a real PASS, a visible pad and pad movement <= 6 px

# full fit only if the check fails
python3 -u ~/codes/calib3d.py
python3 -u ~/codes/calib3d.py --check

# vendor red-square one-key: needs DISPLAY (see below)
cd ~/spark_noetic && ./onekey.sh    # 8, uArm, align pad in green box, confirm
ls -l ~/thefile.txt

Vendor one-key from SSH — DISPLAY export

The one-key opens OpenCV windows (win_draw, win1, win2) and a gnome-terminal confirm prompt. An SSH session has DISPLAY unset, so nothing appears. Export the robot's own desktop (:0, mirrored by x11vnc on port 5900) before running:

ssh spark@<robot-ip>
export DISPLAY=:0
export XAUTHORITY=$HOME/.Xauthority
xdpyinfo >/dev/null && echo "display OK"   # sanity check

bash ~/codes/robot/stop_sim.sh             # free the CPU; the one-key starts its own stack
cp ~/thefile.txt ~/thefile.txt.bak         # the one-key overwrites it, keep a rollback
cd ~/spark_noetic && ./onekey.sh
#   8 = arm-camera calibration, 2 = uArm, Enter for the A/B/C checklist

Watch the windows over VNC at <robot-ip>:5900 (credentials as configured on the robot; not stored here). Keep DISPLAY per-session and never put it in ~/.bashrc: ROS/system services would inherit it. To show the windows on the PC instead of VNC, use ssh -Y spark@<robot-ip> (SSH sets the forwarded DISPLAY itself); live video is laggier that way.

Green-box step

win_draw shows the camera with a 20×30 px green rectangle at pixel (355, 310) and the text "move the camera to make the red color in the rectangle green box". Move the camera until the calibration pad on the suction head is inside that box (centre ≈ pixel 365, 325). The pad colour is learned from the box contents, so the blue-circle vs red-pad wording in the vendor files does not matter. Then confirm in the send_topic.sh prompt (是否已经把绿色框对准了机械臂的红色标定点？, any key).

# after confirming
# 1. HSV sampled from inside the box for ~5 s (200 frames)
# 2. cali_pos.py sweeps the arm through 20 poses (x 180->275, y 200->10, z -110)
# 3. two linear regressions fitted; result written to ~/thefile.txt  (k1 b1 k2 b2)

If the confirm window does not open (gnome-terminal/DBus hiccup), run the publisher by hand with DISPLAY=:0 set:

bash ~/spark_noetic/src/spark_app/spark_carry/scripts/send_topic.sh

Verified on the Spark 2026-11-23: DISPLAY=:0 XAUTHORITY=$HOME/.Xauthority xdpyinfo succeeds, ~/.Xauthority is owned by spark (mode 600), and x11vnc listens on 5900 mirroring :0.

The one-key can move the camera. Re-run the DLT check afterwards. If the D435 logs Frames didn't arrive within 5 seconds, unplug/replug the camera USB or reboot before starting the normal stack. Do not run the one-key and the normal driver_bringup/arm stack at the same time; the one-key starts its own base, camera and arm.

5. Detection bridge on the real robot

The real D435 image is top-down while the URDF camera TF is horizontal. Do not use pinhole mode on the robot; use the production DLT matrix.

# Passive projection check against a measured cube (base frame)
python3 -u ~/codes/bridge_check.py \
  _mode:=dlt _matrix:=$HOME/codes/transform_3d.dat \
  _target_frame:=base_footprint \
  _expected_class:=bear _expected_x:=0.30 _expected_y:=0.00 \
  _samples:=20

# Map frame (AMCL/nav running)
python3 -u ~/codes/bridge_check.py \
  _mode:=dlt _target_frame:=map \
  _expected_class:=cake _expected_x:=1.5 _expected_y:=1.5

# Live bridge + RViz markers (base frame; FRAME=map for map)
bash ~/codes/robot/run_detection_view.sh
FRAME=map bash ~/codes/robot/run_detection_view.sh

# Bridge only
python3 ~/codes/detection_bridge.py \
  _mode:=dlt _target_frame:=map \
  _matrix:=$HOME/codes/transform_3d.dat \
  _world:=$HOME/codes/config/arena_map.yaml _debug:=true

DLT heights: floor cubes z=-100 mm, cake z=0 mm. Arm mount: base_link -> Base = (0.044, 0, 0.138), no rotation.

Verified passive result

Real detector, no movement: bear at base (0.246, -0.010) m, arm (202, -9.6) mm, stable to 1–2 mm. /detections_world_test carried {"class":"bear","confidence":0.93,"x":0.246,"y":-0.01}.

Acceptance and troubleshooting: docs/BRIDGE_VALIDATION.md.

5b. Scan and back: D → W → D

Validated on the real arena (2026-11-22/23). Starts in the D collection square, drives to the west sorting stand-off, scans, and returns to D. Uses the sorting points after the 3 cm outward bias and the tighter goal tolerance from ~/codes/config/move_base_tuning.yaml.

Before starting

Place the robot in the D collection square: wheel-axle centre at (0.225, 0.225), 22.5 cm from the south and west walls, nose at +45° towards the arena centre. Keep the charger out of the drive path — a step under the wheels corrupts odometry and makes AMCL drift.

Terminal 1 — chassis and camera

source /opt/ros/noetic/setup.bash
source ~/spark_noetic/devel/setup.bash
roslaunch spark_bringup driver_bringup.launch camera_type_tel:=d435 lidar_type_tel:=ydlidar_g6

Terminal 2 — lidar (driver_bringup does NOT start it)

source /opt/ros/noetic/setup.bash
source ~/spark_noetic/devel/setup.bash
roslaunch lidar_driver_transfer ydlidar_g6.launch

Wait for /scan at ~10 Hz (rostopic hz /scan) and /odom at ~12 Hz (rostopic hz /odom). If /odom is silent after a power cycle, the base's USB re-enumerated: rosnode kill /spark_base_server then roslaunch spark_base spark_base.launch serialport:=/dev/sparkBase.

Terminal 3 — map + AMCL + move_base

source /opt/ros/noetic/setup.bash
source ~/spark_noetic/devel/setup.bash
export INIT_X=0.225 INIT_Y=0.225 INIT_A=0.785398
bash ~/codes/nav_bringup.sh

Check that AMCL agrees with where you placed the robot and that the tuned tolerance is live:

rosrun tf tf_echo map base_footprint
# expect ~ (0.225, 0.225) and 45 deg

rosparam get /move_base/DWAPlannerROS/xy_goal_tolerance
# expect 0.03

Terminal 4 — drive, scan, return

# D -> W: west sorting stand-off, facing the cluster
python3 ~/codes/go_point.py 1.09 1.50 0

# Optional: see what the camera reports at W
python3 ~/codes/detect_ros.py _augment:=true &
python3 ~/codes/detection_bridge.py _mode:=dlt _target_frame:=map \
  _matrix:=$HOME/codes/config/transform_3d.dat \
  _world:=$HOME/codes/config/arena_map.yaml
rostopic echo /detections_world

# W -> D
python3 ~/codes/go_point.py 0.225 0.225 45

Each goal prints RESULT ok=True state=3 (SUCCEEDED). Expected arrival is within ~2 cm and ~5°; the yaw reading is AMCL estimate noise. The detector's cake gate is 0.90 for cake and 0.60 for cake_site (wine = class 2/20); with _augment:=true the cake is reported at ~0.8–0.9 from the west side.

Stop

# stop motion, keep the navigation stack up
rostopic pub -1 /move_base/cancel actionlib_msgs/GoalID "{}"

# stop the navigation nodes
rosnode kill /move_base /amcl /navigation_velocity_smoother

Terminals 1 and 2 are stopped with Ctrl-C. If the robot does not stop, power it off. Do not drive over the charger.

7. Deploy to Spark

One command from this PC. It stops a sim left running by an earlier deploy, copies the whole simulation tree into the ~/codes layout the run scripts read, refreshes the robot's rospack index and prints a preflight. Safe to re-run after any edit: rsync sends only changed files.

bash "$HOME/Documents/Extra/ROS Comp/simulation/robot/deploy.sh" spark@<robot-ip>
# or from simulation/:  bash robot/deploy.sh spark@<robot-ip>

Target layout on the robot:

In the repoOn the robotRead by
codes/~/codes/ all nodes ($HOME/codes/*.py)
config/~/codes/config/ mission, gate, world, move_base tuning
maps/~/codes/maps/map_server
ros/~/codes/ros/ nav launch files, RViz layout, nav bring-up copy
robot/~/codes/robot/ start/stop/run scripts (+x)
gazebo/arena.world, gazebo/spark_arena.launch, assets/spark1_description/urdf/spark1_description_nav.urdf ~/codes/sim/start_sim.sh
assets/ (auto_match, spark1_description) ~/codes/assets/ fallback packages between the vendor copy and the sim deploy

The deploy also runs rospack profile. A stale rospack cache made rospack find auto_match and rospack find spark1_description fail on 2026-11-23 although both are in ~/spark_noetic/src. The deploy preflight must print all three paths:

auto_match:         .../spark_noetic/src/3rd_app/auto_match_25/auto_match
spark1_description: .../spark_noetic/src/spark_app/Gazebo_demo/src/spark1_description
gazebo:             /usr/bin/gzserver

start_sim.sh appends ~/codes/assets to ROS_PACKAGE_PATH after sourcing spark_noetic, because ROS's setup.bash resets that variable (exporting it before the script is lost). Vendor packages stay first on the path; the bundled auto_match and model are the fallback.

Erase a deploy — only when ~/codes is sim-only:

ssh spark@<robot-ip> 'rm -rf ~/codes ~/logs/sim'
